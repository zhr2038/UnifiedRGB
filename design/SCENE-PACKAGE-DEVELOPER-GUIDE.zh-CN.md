# 光域场景包开发规范 v1 / v2 / v3 / v4

## 适用版本与兼容原则

本规范面向主题场景作者。场景包提供灯光帧和屏幕素材；光域负责校验、设备接管、逻辑灯位映射、共享时钟、播放和本机设备绑定。添加符合本规范的新主题不需要修改或重新编译程序。

支持的版本组合：

| 字段 | 固定值 |
| --- | --- |
| `format` | `UnifiedRgb.ScenePackage` |
| `schemaVersion` | `1`、`2`、`3` 或 `4` |
| `playbackContract` | `rgb24-hold-physical-ms-v1` |
| `loop` | `true` |

v1 支持纯灯光、纯屏幕和二者组合。v2 在屏幕轨道上增加两个可选字段 `accentColor` 和 `overlayLayout`（见下文“v2：电脑数据区域”）。v3 在 v2 基础上允许明确的 MP4/H.264 SDR 素材及其较高发送目标。三个版本的播放契约均为 `rgb24-hold-physical-ms-v1`；v1 包的字节、含义和拒绝规则不变，v1 包中出现 v2 字段（包括值为 `null`）仍会被拒绝，v1/v2 仍拒绝 MP4。内容不执行包中的代码；不支持脚本、插件 DLL、HTML、网络数据源或自定义执行器。动态电脑数据由程序自己的采集器提供。

v4 增加显式、有界的 MP4 分段长轨，见下文“v4：分段背景”。旧版单文件语义保持不变。

程序更新不能偷偷重画、迁移或重新解释旧包。未知版本（如 `schemaVersion` 5）、缺失文件、校验失败和无法准确播放的内容应明确拒绝。旧草稿格式 `UnifiedRgb.ScenePackage.Draft` / `…-draft` 不能直接导入，须由作者显式重新发布为受支持版本。

本规范按以上固定契约定义；具体功能可用性以程序版本和发布验收记录为准。

## 快速开始

开发工具只需要 Python 3.10 或更高版本，不需要第三方 Python 库。**运行光域本身不需要 Python。**

在克隆后的项目根目录执行：

```powershell
python .\tools\scene-packages\pack_scene.py sample .\my-scenes\aurora
# 修改新目录中的 scene.json、lighting/*.rgb24、screens/*。
python .\tools\scene-packages\pack_scene.py build .\my-scenes\aurora .\my-scenes\aurora-r1.zip
```

在“场景库 → 外部场景包”导入 ZIP，查看首帧，为每个角色选择本机灯区或屏幕，点击“保存设备绑定”，最后点击“应用场景包”。导入、首帧预览和保存绑定不会切换当前播放内容。

项目内已有可参考的最小示例：`assets/scenes/examples/aurora-starter/`，以及对应的 `aurora-starter-v1.zip`。它包含一条 8 灯位灯光轨道和一个静态屏幕背景；其设备选择需要在本机完成。

## 包目录与清单

ZIP 根目录必须直接包含 `scene.json`，不能再套一层主题目录：

```text
scene.json
lighting/strip.rgb24
screens/panel.png
README.md                  可选，须列入 files 校验表
bindings.template.json     可选、仅供人阅读，不自动绑定设备
```

下面是清单结构。示意校验值必须由打包工具换成完整 SHA-256；不能原样导入。

```json
{
  "format": "UnifiedRgb.ScenePackage",
  "schemaVersion": 1,
  "id": "aurora-starter",
  "name": "极光 · 入门示例",
  "revision": 1,
  "durationMs": 12000,
  "loop": true,
  "playbackContract": "rgb24-hold-physical-ms-v1",
  "lighting": [
    {
      "role": "accent-strip",
      "label": "装饰灯条",
      "file": "lighting/strip.rgb24",
      "ledCount": 8,
      "frames": 200,
      "frameDurationMs": 60,
      "pixelFormat": "RGB24",
      "pixelOrder": "logical-layout",
      "brightnessBaked": 1
    }
  ],
  "screens": [
    {
      "role": "main-panel",
      "label": "主画面",
      "file": "screens/panel.png",
      "durationMs": 12000,
      "overlay": "dashboard",
      "fit": "contain",
      "fps": 5
    }
  ],
  "files": {
    "lighting/strip.rgb24": "此处是完整的64位小写SHA256",
    "screens/panel.png": "此处是完整的64位小写SHA256"
  }
}
```

`id` 是主题系列标识，符合 `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`。`name` 可用中文，1～128 个可显示字符；`revision` 是正整数。程序实际按内容哈希区分安装版本，不以显示名称覆盖旧内容。

`role` 是作者定义的内容角色，符合 `[a-z0-9][a-z0-9-]{0,63}`。所有灯光和屏幕角色必须共同唯一。`label` 可选，1～64 个可显示字符，省略时显示 role。角色不能写成本机 MAC、USB 路径或控制器 ID。

清单不接受注释、尾逗号、重复键和未声明的扩展字段。作者、授权和制作说明可写入 `README.md`，不要随意往 `scene.json` 增加字段。`lighting` / `screens` 可省略不用的一类，但合计至少有一条轨道。

`files` 列出全部数据文件及完整小写 SHA-256，不能包含 `scene.json` 自己。ZIP 只能携带清单和这些已声明文件；允许的额外惰性文件只有根目录 `README.md`、`README.txt`、`bindings.template.json`，也必须列入校验表。打包工具会收集这些文件并生成校验表。

## 灯光帧格式

灯光文件使用 `.rgb24` 后缀，无文件头，无压缩，无颜色表：按“帧 → 灯位 → R、G、B”依次存放，每通道为一个 0～255 字节。

```python
offset = (frame_index * led_count + led_index) * 3
data[offset:offset + 3] = bytes((red, green, blue))
```

文件长度必须严格等于 `frames × ledCount × 3`。示例为 `200 × 8 × 3 = 4800` 字节。所有灯光轨道的 `frames` 和 `frameDurationMs` 必须相同，且其乘积等于包的 `durationMs`。

`pixelOrder` 固定为 `logical-layout`：写逻辑灯位顺序，不写 USB 包、硬件寄存器或线序 BGR。作者负责算出每一帧的颜色、运动、波浪、堆积或渐变；底座保持这些帧，不重新运行某个主题生成器。

`brightnessBaked` 可省略，填写时为 0～1 的制作元数据。例如作者已经按 70% 生成像素，写 `0.7` 用于说明，程序不能再乘一次 0.7。包默认按 100% 内容亮度、中性速度播放；设备安装映射和硬件色彩处理仍属于本机配置。

当前机箱的逻辑灯位基线如下，仅用于制作选型；绑定时必须以程序实际发现的布局为准：

| 灯区 | 逻辑灯位 | 制作提示 |
| --- | ---: | --- |
| 底排、侧排、顶排，各三颗风扇 | 各 78 | 每颗两条 13 灯位边缘，共 26；安装反向由本机处理 |
| 冷头环 | 24 | 作者生成环形帧；不要重复烘焙本机已校准的安装偏移 |
| 两条内存 | 各 8 | 当前布局上到下排列；包角色分别绑定两条 |
| 主板 ROG | 2 | 两个漫射控制区域，不是两个边界清晰的独立图像像素 |
| 显卡正面竖条 | 12 | 当前布局下到上；相应实体竖条共享控制关系 |
| 显卡横条及共用菱形区域 | 4 | 菱形不是已确认可独立控制的分区，不要新增虚构角色灯位 |

v1 要求灯位数完全匹配目标区域，不做插值拉伸或自动重采样。不同机型需要作者提供匹配其逻辑布局的内容版本，或使用相同灯位数量的通用角色。

## 屏幕素材与电脑数据

v1/v2 支持 PNG、JPEG 和 GIF；v3 另支持下节规定的 MP4。静态图片保持整个循环；多帧素材的实际解码总时长必须等于该轨道和整包的 `durationMs`，不会自动拉伸时间。

GIF 延时以百分之一秒保存。程序把低于 20 毫秒的延时（包括 0 和 10 毫秒）解释为 100 毫秒；制作时请使用明确的至少 20 毫秒延时。推荐每帧 60 或 100 毫秒，并检查所有延时的和。单帧 GIF 按静态图处理。

| 字段 | 值与效果 |
| --- | --- |
| `overlay` | `none` 只显示素材；`compact` 精简电脑信息；`dashboard` 完整监控面板 |
| `fit` | `contain` 完整显示并留黑边；`cover` 填满、居中裁切 |
| `fps` | PNG/JPEG/GIF 为 1～15；v3 MP4 为 1～60。发送目标频率，不是素材或全局时间的加速倍率 |

电脑数据来自底座自己的实时采集器，未获取到的数据应显示不可用。包不放入硬件监控 SDK、厂商程序或采集脚本。若选择 overlay，请为信息层留足对比度和可读空间；自定义角色、字体和装饰可先渲染进背景。v1 的动态信息布局限于上述内置两种面板，不执行自定义页面代码；v2 可以把完整面板放进指定区域并指定强调色，仍不执行页面代码。

建议制作画布：风扇屏 400×400、冷头屏 480×480、机箱长屏 1920×480。圆形屏幕的四角不可见，关键文字和角色应放在内接圆内。旋转和实体屏幕位置属于本机设置；v1 包本身没有 `rotation`、背光或 USB 地址字段。

程序可能把解码画面等比例缩小到最长边 1920 后生成自己的播放缓存；原始包和素材仍保留。GIF 的每个源帧不等于都能在实际屏幕上发送：发送频率和 USB 吞吐较低时按共享时间取当前画面，不能把帧数当实际设备 fps。

## v3：MP4 背景与统一时间轴

只在需要 MP4 时把新包明确发布为 `schemaVersion: 3`。结构沿用 v2，不增加播放器、旋转或质量字段。屏幕轨道示例：

```json
{
  "role": "video-panel",
  "file": "screens/background.mp4",
  "durationMs": 16000,
  "overlay": "dashboard",
  "fit": "cover",
  "fps": 30,
  "overlayLayout": {"x": 0.55, "y": 0.1, "width": 0.43, "height": 0.8, "columns": 2, "backgroundOpacity": 0.5}
}
```

- MP4 目前仅接受 H.264/AVC、SDR 8-bit、方形像素；音频不播放。不支持 HDR/广色域、非单位轨道矩阵或旋转元数据，请先导出方向正确的像素并清除旋转元数据。本机安装方向仍独立保存。
- 每文件最多 12 MiB、30 秒、1800 帧，至少 48×48，单幅解码仍限 4000 万像素，归一化 PNG 合计最多 256 MiB。解码循环检查 90 秒工作预算和读取次数；导入阶段依赖同步 Windows 媒体组件，不宣称能强制中断其内部调用。
- 第一幅视频画面的呈现时间归零，其余相对 PTS 保留，按毫秒取整；不使用 GIF 的短延时=100ms 规则。解码得到的完整循环必须精确等于清单时长。可变帧率输入也按 PTS 处理，发送目标不会改变播放速度。
- 程序在导入时生成全色 PNG 帧缓存，原 ZIP/MP4/内容哈希保持原字节；不是把影片转为 GIF。包中拒绝外部媒体引用，不接受 URL，也不调用厂商程序或 FFmpeg。
- v3 MP4 轨道允许 1～60 的发送目标；PNG/JPEG/GIF 仍为 1～15。目标不等于设备可见帧率。RGB24 的物理毫秒、逻辑灯位与 v1/v2 完全相同，不自动提高灯光速率。
- 所有包轨道仍使用共同 `TimelineId`。通常由 Host 按主时钟选择当下的帧，落后则跳过过期画面，不建立各屏独立媒体时钟。原生 H.264 是可选的长屏传输策略，不是新的包语义。
- 长屏原生策略使用独立关键帧和独立透明 PNG 实时信息层。它有 YUV 4:2:0/有损背景编码的取舍，必须单独验证设备方向、同步、循环和信息更新；默认关闭。不能把 Windows 解码成功、USB ACK 或传输速率当成设备显示验收。
- v1/v2 仍拒绝 MP4；旧包无需重打包。作者工具不解码视频，也不能证明时长或设备兼容。用 `sample --schema 2` 创建结构后，作者显式修改为 3 并加入自己的 MP4，再用 `build` 打包、在 Windows 程序中验证；没有隐式升级或自动生成视频示例。

## v4：分段背景

v4 屏幕轨可以用 `segments` 代替单个 `file`。两者不能同时出现；v1/v2/v3 出现 `segments`（包括 `null`）仍被拒绝。每段只能包含以下两个字段，段序就是播放顺序：

```json
{
  "role": "main-panel",
  "segments": [
    { "file": "screens/main-00.mp4", "durationMs": 24000 },
    { "file": "screens/main-01.mp4", "durationMs": 24000 }
  ],
  "durationMs": 48000,
  "overlay": "dashboard",
  "fit": "contain",
  "fps": 24
}
```

- 每轨 2～32 段，只接受 MP4/H.264 SDR；每段 1～30000 整数毫秒、最多 1800 帧、12 MiB。源画布须为正向方形像素，每轴 48～1920 像素，所有段画布相同。
- 解码 PTS、末帧驻留和段时长必须一致；段时长总和精确等于轨道及整包时长。每轨总时长最多 600 秒、36000 帧、64 MiB 压缩源，索引最多 512 KiB。验证时有逐段及整轨工作预算，取消不会发布半成品。
- 每个 MP4 都列入 `files` 的 SHA-256 校验表。轨的资产身份由有序的“段哈希＋段时长”决定，保护绑定、重启、配置恢复与删除引用。
- 分段资产保留压缩原片和有界索引；不把整段长片预解码成大量 PNG。每个合成器只有当前片段的 STA 解码器和当前栅格。现有有界编码缓存仍独立生效。
- 所有段使用同一个场景时间轴。换段、反向定位或循环不重置场景纪元，不启动每屏独立时钟。读取失败明确输出 `BLOCKED` 黑帧，不改成别的背景。
- ZIP 仍最多 64 MiB、128 条目，展开仍最多 256 MiB；每段占一个条目。九路 RGB 的帧数和 32 MiB 限制不变。原生传输、本机质量、旋转、安装和背光仍属于本机策略。
- 作者工具只检查包结构和字节预算，Windows 导入器负责完整解码验证；不能把目标 FPS 当成可见帧率。

## v2：电脑数据区域

适合“画面一侧是动画角色，另一侧显示真实电脑状态”的长条屏。背景动画（包括划过数据区域的闪电等）照常画在素材里；程序只在指定区域上方叠加实时数据，数值本身不做动画。

```json
{
  "role": "wide-panel",
  "label": "宽屏画面",
  "file": "screens/panel.gif",
  "durationMs": 12000,
  "overlay": "dashboard",
  "fit": "cover",
  "fps": 10,
  "accentColor": "#FAD61D",
  "overlayLayout": { "x": 0.5, "y": 0.16, "width": 0.48, "height": 0.74, "columns": 2, "backgroundOpacity": 0 }
}
```

| 字段 | 规则 |
| --- | --- |
| `accentColor` | 可选，严格 `#RRGGBB`；用于标签和细分隔线。`overlay` 为 `none` 时不允许 |
| `overlayLayout` | 可选对象，**恰好**包含下列六个字段，多一个或少一个都拒绝；`null` 也拒绝。只能与 `overlay: "dashboard"` 一起使用，`compact` 不支持区域 |
| `x`、`y` | 有限数，0～1，区域左上角，按内容画布比例计算 |
| `width`、`height` | 有限数，大于 0 且不超过 1；同时须 `x + width ≤ 1`、`y + height ≤ 1` |
| `columns` | 整数 1～4（不接受 `2.0`、`"2"`）；行数 = ⌈4 / columns⌉ |
| `backgroundOpacity` | 有限数 0～1；0 表示没有底板，只有带柔和阴影的文字，适合让背景动画完整透出 |

区域坐标针对**内容画布、在本机安装方向旋转之前**：机箱长屏按 1920×480 的横向画布设计即可，本机设置 90/180/270° 后整个画面（含数据区域）一起旋转，不需要在包里另做方向版本。

区域显示四项：CPU 占用、GPU 占用和可用温度、内存已用/总量、显存已用/总量。文字大小随区域和列数等比计算，并按 100%、105 °C、256 GB 及缺失值“—”的最长情况统一确定，数值变化时字号不跳动。超过 5 秒未更新的数据视为缺失，显示“—”而不是 0；程序不会编造 CPU 温度等未采集的数据。区域外的像素保持完全透明，内容不会画出区域。

区域**只支持矩形屏幕**（如机箱长屏）。把带区域的角色绑定到圆形风扇屏或冷头屏时，保存绑定和应用都会明确拒绝，原场景保留；程序不会丢弃区域或把它扩大成全屏面板。不带 `overlayLayout` 的 v2 屏幕轨道与 v1 行为相同。

## 共享时间与同步

所有时间都写**真实毫秒**。`200 帧 × 60 毫秒 = 12000 毫秒`，不是标称硬件单位。无线主控每秒 1600 tick，60 毫秒由底座转换为 96 tick，作者无需自行写 96。不能精确表示的无线驻留时间会拒绝，不做暗中取整。

灯光帧按驻留时间保持，不做帧间插值。建议把循环末尾设计为能自然衔接首帧，不要依赖“播完最后一帧再调用脚本”的结束事件。包中没有多个独立的设备起始时间。

有无线灯光时，原生灯光和屏幕跟随同一包的共享参考时间；纯屏幕或纯流式输出使用共同的单调时钟起点。冷启动、时钟失效或设备离线要看程序实际诊断，发送成功不等于光学同步已经验收。素材内容不变不等于任意硬件都具有相同刷新率、色彩和亮度。

组合包的灯光退出播放计划后，依赖该计划的包屏幕会暂时黑屏并提示阻止原因，不另起一个私有时钟继续错位播放。例如对组合包执行“全机熄灯”后，要用“恢复”一同恢复共享播放。独立屏幕内容不受这一包时钟规则影响。

## 本机设备绑定

内容包使用角色，设备绑定单独保存在本机。主题作者不应把控制器 ID、内存地址、MAC 或 USB 实例写进发布清单。

每个灯光角色绑定一个存在的灯区，灯位数量必须完全相等；每个屏幕角色绑定一块可用屏幕。两个角色不能重复绑定同一目标。未绑定、设备离线、输出未开启或被其他写入器占用时，应先解决问题再应用。

保存绑定只保存配置，不发测试颜色，不自动开启输出。保存成功也不一定代表当前可以播放，须看“绑定已就绪”和实际设备状态。后续修改绑定会生成新绑定快照；已保存的场景仍指向原来的绑定版本，不能偷偷改投新设备。

## 安装、更新与恢复

程序按原始 `scene.json` 的 SHA-256 生成 ContentId；清单中的素材哈希进一步固定内容。即便只修改清单空白，内容 ID 也可能变化。同一内容重复导入是幂等安装；同名新修订是新条目，不覆盖旧包。

修改主题时保留旧发布 ZIP，提高 `revision`，重新打包为新文件名，然后导入和绑定。不要直接编辑程序的已安装内容目录，也不要用程序升级重新生成旧主题素材。

运行状态和已保存场景记录内容 ID、绑定 ID 与播放契约。内容缺失、损坏或契约不支持时应阻止播放并提示；重新导入正确原包并应用，而不是删除引用后换成一个看似相近的效果。包内屏幕素材受保护，普通素材删除入口不能破坏已安装主题。

应用前会检查全部候选目标及真实无线压缩预算。无法完整容纳时拒绝整个候选，保留原场景；不会悄悄抽帧、缩短循环或替换为单色。通过导入不代表已经通过设备绑定、实际无线预算和视觉验收。

## 开发工具与示例

`tools/scene-packages/pack_scene.py` 是**制作辅助工具**，不是运行时验证器：

1. `sample` 创建最小 v1 素材目录，便于复制成不同主题；`sample --schema 2` 创建带电脑数据区域的 v2 示例（宽屏右半边、两列、强调色 `#FAD61D`）。默认 v1 输出与之前逐字节相同。
2. `build` 做基本结构、RGB 长度、路径和大小检查（v2 还检查 `accentColor` 和 `overlayLayout` 的全部规则，v1 中出现这两个字段即拒绝），收集引用素材，计算完整 SHA-256，生成确定性的 ZIP。
3. 它不修改源素材或旧发布 ZIP，输出已存在时拒绝覆盖。
4. GIF/MP4 解码时长、图像解码预算、全部清单约束、设备可用性、安装映射和无线容量由程序正式校验。打包工具通过后仍必须在程序中导入并应用检查。

修改已有示例：复制整个 `aurora-starter` 目录到自己的工作目录，改 `id`、`name`、`revision` 和素材。源清单的 `files` 可为空；打包工具在输出 ZIP 内写入实际校验表，程序则要求最终 ZIP 的校验表完整。

给其他开发者或 AI 的任务描述可以是：

> 根据《光域场景包开发规范 v1》制作独立数据主题。只交付 scene.json、逐轨 RGB24 和 PNG/JPEG/GIF 素材，不修改光域源代码，不依赖厂商程序。所有灯光轨道共用指定帧数和真实毫秒间隔；屏幕动画总时长相同。逻辑灯位数按目标清单准确制作，角色与本机设备绑定分离。用 pack_scene.py 打包，保留可编辑的源素材，并提供循环衔接和实机验收说明。

## 验收与常见问题

交付时至少检查：

- 原 ZIP、源素材和清单能对应；打包生成的哈希完整。
- 首帧、最后一帧和循环边界正确，没有忘记清空或突跳。
- 所有角色准确绑定，灯位数量一致；没有独立菱形等未支持区域。
- 导入和预览不改变当前场景；设备不就绪或无线超预算时，原场景保留。
- 完整一轮的运动方向、亮度和屏幕朝向由人观察确认。
- 保存、重启、重新读取后，内容与设备绑定仍指向同一发布版本。

**颜色/速度看起来不对：**先核对 RGB/BGR、是否把真实毫秒误写成硬件 tick，以及是否把安装反向重复烘焙。不要用每设备私有加速倍率掩盖时间单位错误。

**GIF 时长不符：**按程序的低延时规则重新累计，不能只看设计软件的 fps 标注。静态图允许整轮保持；多帧 GIF 必须匹配整包时长。

**显得暗：**检查作者像素值和是否重复缩放亮度。屏幕像素亮度、硬件背光和素材本身的明暗不同；v1 包不设置硬件背光。

**导入成功却不能应用：**导入只证明数据被接受；设备状态、绑定和真实无线容量在后续阶段检查。查看具体问题，不以“导入成功”当全机播放验收。

**想增加新表现形式：**现有逻辑灯位上的任意预渲染动效和支持的背景组合可以作为新数据包制作。新硬件、其它视频编码、其他动态信息布局或执行语义需要底座另加明确版本支持，不要伪造字段或修改旧契约含义。数据区域可使用 v2；MP4 必须显式使用 v3，不往旧包里偷加新字段或格式。

## 本机安装方向与 PNG 编码策略（底座通用设置）

“屏幕内容 → 本机屏幕设置”中的安装方向和编码质量单独保存。按完整 `ScreenId` 记录在本机数据目录的 `screens/device-settings.json`，不属于场景内容或角色绑定。支持顺时针 0/90/180/270°。首次升级从已保存的屏幕场景迁移非零方向；新屏幕默认 0°，编码默认 `legacy`。此后有本机设置的屏幕以本机值为准，应用其他包、保存/恢复普通场景和重启都不会用旧场景值覆盖它。修改后需显式点击“保存设备设置”，不会顺带应用尚未保存的内容草稿或恢复已暂停的输出。

兼容旧屏幕 API：直接 `SetScreenScene` 可以从明确的非零值建立尚无设置的屏幕方向；已有本机设置后，只有专门的设备设置 API 能修改它。包和配置档恢复只读取方向，不写入方向。普通 RGB 场景不附带屏幕时不受影响。

TURZX 的用户方向在合成阶段只处理一次。编码器把 1920×480 的横向画布转换到设备 480×1920 光栅时，仍单独使用底层 `TurzxLandscapeRotation` 的 90/270°映射；这不是用户安装方向，不能合并计算、烘焙进素材或再发送旋转命令。v1 清单仍没有 `rotation` 或编码质量字段，原包、素材字节和内容哈希均不因本机选择改变。

| 本机策略 | 行为 |
|---|---|
| `legacy`（默认） | 保持原有 WIC PNG 8→6→5bit 阶梯和输出字节。不会静默升级为新策略。 |
| `lossless-first-v1`（显式选择） | 全色 PNG 已能装下时逐字节保留；超预算才尝试有界 RGBA8 无损滤波/Deflate 优化，然后依次尝试 6/5bit，各档先试原编码。没有 4bit、截断或放宽协议容量。 |
| `jpeg-detail-v1`（显式选择） | TL/H2 JPEG 从 Q100 开始，按 100/95/90/80/70/60/50/40 有界回退，保留原 JPEG 协议容量。TURZX PNG 明确拒绝此策略。它不改变源素材、背光、安装方向或时间轴。 |

PNG 优化器只使用已支持的非交错 RGBA8 PNG，保持图片上限 **524288 字节**。每个深度最多两种滤波压缩组合，最多 1920×480 像素；临时优化任务串行，编码结果以 96 MiB/512 项 LRU 缓存，缓存键包含像素、尺寸、内部光栅映射和策略。首次复杂帧较慢，缓存不持久化；实时数据覆盖层会改变缓存键，不能假定每帧命中。它不会在 RGB 时钟线程训练调色板或额外读取文件。JPEG 风扇屏、冷头屏在默认和 PNG 保色策略下仍维持原编码，只有显式选择 `jpeg-detail-v1` 才提高 JPEG 质量。

本机三块 Wireless TL 已用真正960帧/16000ms的60fps MP4做限时实测，主机事务约59.56次/秒，用户确认流畅；这不是所有设备的性能保证或相机呈现帧率测量。制作60fps背景须使用独立60帧/秒的动作源，并在v3轨道设 `fps: 60`；把30fps文件改标签、重复帧或单独提高发送目标不会产生新动作。60fps按毫秒归一化时会出现16/17ms源帧驻留，完整循环必须仍精确匹配灯光时间轴，不要把每帧硬写成16ms造成周期缩短。JPEG质量策略仍只属于本机，不写入v1/v2/v3清单；画质、发送目标和源动作帧率是三个不同维度。

调色板/Indexed8 是离线研究路径，当前不可选。Windows 解码成功和标准 PNG 合法均不能证明具体固件接受该色型；配置里的能力标记也不能解除本版本的拒绝。需要另行取得固件支持证据，并证明毛发、暗部渐变和连续帧效果有收益，才可发布新的可选策略。

生成预览会使用已保存的本机方向和质量，解码实际待发送的 PNG/JPEG 字节后显示，因此 JPEG 损失和 PNG 降色也会出现在预览里。未保存的设备设置会提示；编码失败或超预算时清空旧预览并报告失败，不拿未编码原图冒充成功。预览不发送硬件命令，也不等于实际播放或吞吐验收。

区域绑定还会按本机方向检查实际像素尺寸，每个读数至少需要24×24像素；过小会明确拒绝，不静默变成不可见数据层。

### 控制单位是灯珠，不是键帽

同一键帽下面可以有多颗灯珠。当前空格的五颗使用五个独立颜色槽，分别标注 `Space.L2`、`Space.L1`、`Space.C`、`Space.R1`、`Space.R2`，从左到右排列；可以同时显示五种不同颜色。当前 85 灯位表中它们的逻辑索引为 74–78，原生地址为 37 / 45 / 53 / 61 / 69。**包中只写逻辑索引的颜色，不写这些原生地址。** 后续更换映射后，以本机实际顺序为准，不能把索引示例当所有键盘的固定布局。

本机 85 是已定义的控制位置数，不是“85 个按键”或已证明的全部物理发光器件总数。矩阵地址 12 本轮没有观察到发光；99 在引号键附近呈较弱红光，与 91 的光学关系尚未确认，未把它重复计作独立灯位。不要为了凑数量加入未确认位置或把空格五颗自动合并。

“设备与校准 → 逐灯校准”可点亮单个原生地址、记录实际灯珠的位置并生成映射片段。标签可写按键名，也可写键帽内的灯珠位置；同一键帽内各灯位使用不同标签和坐标。`PerKeyStatusDto.KeyCount` 沿用既有字段名，表示映射记录数，界面显示为灯位数。准备导出的片段不会自动修改设备或场景。

默认的整色跟随会在没有显式键盘轨道时把来源颜色填满已就绪的键盘灯区；这只用于沿用原有整色场景。显式为该灯区绑定 RGB24 后，每一个灯位都使用作者给出的独立颜色，跟随回退不覆盖它。

逐灯发送节奏属于本机设置，不写入场景包。`AsusRog.KeyboardPerKey.MaximumFps` 可选 1–30，仅在逐灯映射就绪时改变主机更新上限；缺省仍为 10。`RfReportDelayMs` 可选 0–8，缺省仍为 8ms；本机无线使用 0 取消人为等待，并实测主机约 30 次完整写入/秒，用户确认快速彩虹比 20 次/秒更均匀。每一帧仍包含全部独立颜色，不合并灯珠或改 RGB24 驻留语义。这是当前无线设备的使用反馈，不是所有设备支持 30fps 的保证；新节奏 USB、OLED 动画并发和长期运行须分别实测。素材可以保留更密的原始帧格，由共享时间轴选择当前帧，勿为追逐发送计数重写灯效时长。

### 可执行的逐灯键盘＋鼠标示例

把本机映射片段保存为单独的 `layout.json`，然后执行：

```powershell
python .\tools\scene-packages\make_peripheral_led_demo.py --layout .\layout.json --out .\my-scenes\peripheral-led-demo
python .\tools\scene-packages\pack_scene.py build .\my-scenes\peripheral-led-demo .\my-scenes\peripheral-led-demo-v1.zip
```

生成器保留映射中的逻辑顺序，不按原生 LED 地址排序；为每个灯位生成颜色，空格五颗分别参与。鼠标使用一条整区轨道，和键盘共用 40 帧 × 100ms 的 4000ms 时间轴。可用 `--frames`、`--frame-ms` 改时长。生成和打包全在离线进行，不导入、不绑定、不应用；`layout.json` 的设备资料、证据和原生地址不会被复制进 ZIP。

导入后，分别把 `keyboard-leds` 绑定到本机 N 灯位键盘区、`mouse-rgb` 绑定到鼠标整区。N 必须精确匹配本机已启用布局；整色一像素轨道不能自动拉伸为 N 灯轨道。加入机箱和屏幕内容时，继续使用原有角色、帧格和共享时间轴，不增加外设专属清单字段。示例是制作入口，不等于任何设备都能达到作者设置的帧率。

### RGB 作者：角色、灯位与本机绑定

1. 在 `lighting` 中使用作者自定角色，例如 `keyboard-rgb`、`mouse-rgb`。它们只是角色名字，不是新增类型；不要向清单增加 `keyboard`、`mouse`、`keyframes` 或 `nativeCode` 等字段。
2. 整区键盘和鼠标各制作一条 `ledCount: 1` 的 RGB24 轨道；逐键键盘只有在本机确实暴露 N 灯位且映射验收完成后才制作 `ledCount: N`。包不能把一个像素自动拉伸到 N 个键，也不能把 N 键轨道降级成整区轨道。
3. `pixelOrder: "logical-layout"` 的第 i 个像素是当前逻辑布局第 i 项，不是原生 LED ID i。逐键布局的顺序来自本机已验证的键表；键名、行列和原生 LED ID 的关系属于本机配置。作者可在离线制作时参考经确认的布局，将 W/A/S/D 对应逻辑索引涂色，或按行列坐标计算左→右波浪 / 预渲染涟漪，再只交付 RGB24。
4. 键名 → 逻辑索引 / 原生 LED ID、设备地址和各传输路线的映射不要写入发布 ZIP、v1 清单或内容哈希。它们保存在本机 `AsusRog.KeyboardPerKey.Maps` 等设备配置中。仅灯位数量相同不保证两种键盘排列相同，跨机型制作仍须核对布局，不能只改标签复用。
5. 全部 RGB 轨道继续共用 `frames`、`frameDurationMs`，相乘等于 `durationMs`。v1 没有逐帧时间戳字段：第 i 帧从 `i × frameDurationMs` 真实毫秒开始驻留。颜色和亮度在 RGB 字节中制作，`brightnessBaked` 只是说明；不要再次缩放。导入后在现有“设备绑定”中把角色绑定到实际发现的键盘 / 鼠标灯区，仍执行精确灯位数检查。

本机灯位表就绪后，可制作 W/A/S/D 高亮、左右波浪、灯珠级渐变和预渲染涟漪；每种具体效果仍应实际观察。本轮验收的是单灯抽测与整表彩虹，不宣称所有效果都已经实测。随真实按键触发的涟漪还需要独立的输入与交互实现，RGB24 包本身没有按键事件脚本。候选键表、协议最大记录数或诊断帧不能单独代替实际映射核对。

### 最小可执行 RGB 示例：两个整区角色

把以下代码存为自己的 `make_peripheral_demo.py`，在项目根目录执行 `python .\make_peripheral_demo.py .\my-scenes\peripheral-demo`。只创建数据目录，不连接设备。两个角色同步保持琥珀色 500ms、黑色 500ms；这只是制作示例，导入和绑定后也须显式应用才会输出。

```python
import json
import sys
from pathlib import Path

root = Path(sys.argv[1])
root.mkdir(parents=True, exist_ok=False)  # 拒绝覆盖旧主题
(root / "lighting").mkdir()
tracks = []
for role in ("keyboard-rgb", "mouse-rgb"):
    file = f"lighting/{role}.rgb24"
    (root / file).write_bytes(bytes((255, 128, 0, 0, 0, 0)))
    tracks.append({"role": role, "file": file, "ledCount": 1,
                   "frames": 2, "frameDurationMs": 500,
                   "pixelFormat": "RGB24", "pixelOrder": "logical-layout",
                   "brightnessBaked": 1})
manifest = {"format": "UnifiedRgb.ScenePackage", "schemaVersion": 1,
            "id": "peripheral-demo", "name": "外设整区制作示例", "revision": 1,
            "durationMs": 1000, "loop": True,
            "playbackContract": "rgb24-hold-physical-ms-v1",
            "lighting": tracks, "screens": [], "files": {}}
(root / "scene.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2) + "\n", encoding="utf-8")
```

再执行现有辅助工具：

```powershell
python .\tools\scene-packages\pack_scene.py build .\my-scenes\peripheral-demo .\my-scenes\peripheral-demo-v1.zip
```

这是一份结构有效的 v1 两轨包；只有目标灯区实际为一个逻辑点时才能绑定。若未来键盘切为已验证 N 键灯区，需要作者生成匹配 N 的另一个内容修订。示例没有屏幕或机箱轨道；加入它们时须保持同一 1000ms 周期，所有 RGB 轨道使用相同帧格，不能另开外设时钟。

鼠标的一像素内容可以由作者对机箱画面选一点或求平均后预先写入 `mouse-rgb`，这属于作者明确的投影选择。另一条现有路径是**本机** `ZoneFollower` 回退：同一渲染 tick 复制一个流式源灯位到未显式分配内容的单点目标；不支持上传循环源、链式跟随或自动平均。显式给鼠标分配场景轨道会优先于该回退。回退关系不写入包，也不改变包时钟。整区外设的实际刷新仍受 adapter / writer 限流；当前键盘代码上限 10 次/秒是主机限制，不能写成逐键或鼠标 60fps 保证。

### OLED 作者：画布、灰度与当前可走的路线

建议按 **208×64** 横向画布制作高对比、大字、简化图形。输出是 16 级灰度（0 黑，15 白），不是彩色屏；低对比彩色素材可能在转换后消失。现有编码为 `luma-round-v1` 或固定 4×4 Bayer 的 `luma-bayer4-v1`，均使用固定亮度公式 `(54R + 183G + 19B + 128) >> 8`，无自适应调色板。可选择 `contain` 留黑边或 `cover` 居中裁切。

传输帧为行优先打包的 4bit 灰度，**每帧 6656 字节**：字节低半字节存偶数像素，高半字节存后一个奇数像素，即 `packed[p] = gray[2*p] | (gray[2*p+1] << 4)`。这是内部编码格式，不是 v1–v4 允许新增的素材后缀或包轨道；作者通常交付 PNG/JPEG/GIF，程序负责转换，不把原始灰度文件伪装成 `screens` 媒体。

目前没有“把屏幕角色绑定到键盘 OLED”的场景包入口，也没有独立 OLED 包字段。现有**本机、默认关闭的动画接口**可从当前已应用的普通屏幕场景取一项素材和它的共享 `TimelineId`，转换为 OLED 帧。具体工作流如下：

1. 用现有包屏幕轨道准备素材，先按本指南将其绑定到受支持的普通屏幕并应用。静态 PNG/JPEG、GIF，以及已通过相应 v3/v4 导入验证的 MP4 / 分段素材均走现有素材库与合成器；OLED 不另设一个媒体导入器。完整循环、缓存和准备时限仍须通过，不能因原屏幕播放正常就假定 OLED 已准备成功。
2. 调用 `IKeyboardDisplayService.GetKeyboardDisplayAnimationAsync()`，从返回的 `Choices` 读取实际 `AssetId`、`TimelineId`。任意上传但尚未进入当前共享屏幕场景的素材，不构成可选项；不要手编标识。现有键盘设置界面也使用同一套接口。
3. Host 动画准入已开启时，通过 `PreviewKeyboardDisplayAnimationAsync(new KeyboardDisplayAnimationPreviewRequestDto(choice.AssetId, choice.TimelineId, "contain", "luma-round-v1"))` 取得少量位置的实际打包灰度预览；准入关闭或准备任务占用时会明确拒绝。`PositionMs` 是素材内位置，`PackedBase64` 是上述 6656 字节帧；解包后检查文字、裁切和灰阶。预览不发送硬件。
4. Host、设备和当前显示 owner 具备相应能力时，可显式调用 `SetKeyboardDisplayAnimationAsync(new KeyboardDisplayAnimationSettingsDto(true, choice.AssetId, choice.TimelineId, "contain", "luma-round-v1", status.MinimumIntervalMs))`。这是 C# 既有契约调用（`status` / `choice` 来自第 2 步），不是写入 `scene.json` 的 JSON 示例。偏好保存在本机 `keyboard-display-animation.json`；更新包或换绑定后需重新选择实际有效项。包时间轴不可用时保留绑定并回退设备空闲动画，不私自另起一个包时钟。

程序按包共享时间选择当下 OLED 帧，不从第 0 帧另起时钟。原生菜单接管、且当前 owner 会话未声明原生画面支持时，通用动画被抑制，保留偏好而不抢写；若固件已声明该能力，现有代码可在入场 Logo 后选择已单独开启、绑定的动画。Host 自绘 Logo 默认约 1.2 秒；设备已自行显示入口 Logo 时，本机 `KeyboardDisplay.DeviceShowsNativeEntryLogo: true` 会跳过第二次 Host Logo 上传，直接衔接后续画面。这只是本机呈现设置，不是包字段，也不能赋予设备原本不存在的播放能力。状态页关闭、素材失效、共享时间轴阻止或上传超时也会导致不同的停止 / 回退状态，须读取返回的 `Admitted`、`State`、`Detail`，不能只看请求中的 `Enabled`。恢复键盘原动画是另一条路径，不与自制场景动画混称。

动画最小上传间隔默认 **2000ms**，Host 允许配置的下限范围为 1000–10000ms，用户设置的间隔不得小于当前返回的 `MinimumIntervalMs`，且不得超过 10000ms。这是选择 / 上传节流，不是保证 0.5fps 或 1fps 可见播放；缓存采样默认 100ms、准备时合并相同灰度帧，也不会提高上传速度。默认整轮灰度缓存 16MiB，最大可配置 32MiB；准备失败不发布部分帧。当前路线不承诺 15/30/60fps OLED、彩色、原生 GIF 文件上传、固件常驻动画或自定义原生菜单项目。

本节代码核对入口：`src/UnifiedRgb.Host/ScenePackages/ScenePackageService.cs`（精确灯位绑定）、同目录 `ScenePackageFrameSource.cs`（`ScenePackageTimeline`）；`src/UnifiedRgb.Host/Services/WiredKeyboardAdapter.cs`、`src/UnifiedRgb.Devices.AsusRog/RogPerKeyPlan.cs`、`src/UnifiedRgb.Devices.Abstractions/PerKey.cs`（本机映射与逐键门禁）；`src/UnifiedRgb.Core/Engine/RenderLoop.Followers.cs`（单点回退）；`src/UnifiedRgb.Screens/Runtime/ScreenManager.Keyboard.cs`、`src/UnifiedRgb.Screens/Keyboard/KeyboardOledFramePreparer.cs` / 同目录 `KeyboardOledEncoder.cs`、`src/UnifiedRgb.Host/Services/KeyboardDisplayAnimation.cs` / 同目录 `KeyboardDisplayService.cs`、`src/UnifiedRgb.Host/KeyboardDisplayOptions.cs`、`src/UnifiedRgb.Contracts/Dto/KeyboardDisplayAnimationDto.cs` / `src/UnifiedRgb.Contracts/KeyboardOledFormat.cs`（OLED 转换、时序和接口）。2026-10-29 用户分别确认 USB 与 RF 路线的单个 Esc 键显示红色；这只是单键验证，不是完整 81 键键表或完整主题验收。

## 本机场景库维护与单屏编辑

“场景库 → 外部场景包”显示安装数量、占用和待清理空间。删除前检查当前灯光、当前屏幕、重启恢复文件、已保存场景及素材恢复任务；存在引用时列出来源并拒绝删除。先切换到其他场景或删除不再需要的保存记录，再重新检查。熄灯前自动备份受保护，不提供删除入口。

删除包保留本机绑定历史，不改写原 ZIP、清单、媒体字节或内容地址。重新导入相同内容后可复用原本有效的设备绑定。“清理无引用素材”默认关闭；打开后仅回收没有当前、恢复、已保存场景或其他包引用的同源屏幕缓存。相同文件曾被单独上传的缓存也可能被回收；库外原文件不受影响。未知文件、链接和损坏内容会阻止删除；文件占用造成的部分清理会如实报告，下次启动重试已确认的库内暂存文件。

应用使用明确的内容地址和预期绑定版本，提交前若绑定变化则拒绝，界面要求重新检查。旧的直接应用 RPC 保留原有“使用当前绑定”语义；新客户端使用独立的检查版本入口，不改变 v1/v2 场景清单含义。

单屏更改叠加、亮度、适配或帧率时保留共享时间轴；更换背景媒体才会请求确认脱离原时间轴。预览仍是实际编码结果、未发送；用户未确认时不改动播放。
