# 长屏原生 H.264 与 MP4 场景支持

## 本轮边界

保留 .NET 8/WPF/MVVM、现有 Host、可信 RPC、设备安装方向和统一时间轴。灯光协议与场景 RGB24 不改；不调用厂商程序、服务、目录或媒体 DLL。当前场景和本机设置按部署前的新鲜快照保护，实机试验仅临时改变一块长屏的传输路径，结束或失败恢复当前图片路径。

## 播放架构

这不是把完整影片交给每块设备自行循环。MP4 先在导入阶段由 Windows Media Foundation 解码，保存完整颜色的 PNG 帧和相对呈现时间；原始素材不经过 GIF 调色板。播放仍由既有 `TimelineId` 的统一时间轴选择当前画面，正常 GIF/PNG 和其它四块屏幕保持原路径。

长屏的原生路径将主时钟选中的背景画面编码成 Baseline H.264 **独立关键帧**：GOP=1、无 B 帧、低延迟、每个访问单元都带 SPS/PPS，并拒绝含预测 VCL 的输出。TURZX 路径最终采用实际0～255的全范围样本，SPS 明确标记全范围、BT.709 原色/矩阵与 sRGB，预览使用同一范围。这样过期画面可直接跳过，循环时可直接选回第一幅画面，不用让设备自己维护循环进度。代价是码率高于通常的帧间压缩影片；是否更流畅须靠设备吞吐与光学测试确认。

实时电脑信息使用独立的透明 PNG 层，只在呈现文字或布局变化时更新。背景不把旧遥测烘焙进缓存，信息层保持当前 CPU/GPU/RAM/VRAM 和时钟。源内容旋转、本机安装方向和长屏转原生光栅的内部变换仍分别处理。图片/视频背景亮度不替代硬件背光控制。

`h264-intra-v1` 是显式本机编码策略，默认不启用；只对单独通过同步、循环、叠加验证的 TURZX ID 开放。切换场景包不强制改变本机策略。未验证设备只能由明确的限时试验入口测试；不能用传输 ACK 自动标成视觉通过。

## MP4 输入与包版本

- 素材库接受 MP4/H.264 AVC SDR、方形像素；不播放音频，不默默进行 HDR 到 SDR 映射。Windows 媒体组件缺失或格式不支持明确失败。非单位轨道矩阵、旋转元数据及非方形像素明确拒绝，要求作者先导出正确像素方向；避免依赖某个 Windows 源读取器是否返回旋转属性。
- 上传上限仍为 12 MiB。MP4 最长 30 秒、最多 1800 帧、归一化 PNG 合计最多 256 MiB，解码工作有时间和读取次数上限；GIF 原有 300 帧和短延迟规则不变。
- MP4 的第一幅视频画面归零，保留相邻 PTS，经毫秒取整生成累积时间轴，不把高帧率 MP4 套进 GIF 的短延迟=100ms 规则。解码时只持有一幅原始光栅和有界的归一化帧表，不保留整段未压缩 BGRA。90 秒预算在读取循环间检查，不能强制中断同步 Windows 媒体组件内部的一次调用。
- 拒绝外部媒体数据引用。系统只打开自身的临时文件，不接受 URL，不调用 FFmpeg。
- 本地 MP4 归一化资产采用显式 metadata v2；原 PNG/JPEG/GIF 的 metadata v1 含义保持不变，临时目录、删除和重启加载认识视频的帧数边界。
- 新场景包 **schemaVersion 3** 才可包含 `.mp4`，此类轨道发送目标可到 60 FPS。v1/v2 仍仅允许 PNG/JPEG/GIF、最高 15；不会根据扩展名或内容静默升级。v3 保留原 RGB24 物理毫秒时间契约、叠加区域和设备绑定。
- 包的真实解码时长必须精确等于声明循环时长，不能自动改速或拉伸。ZIP、原始 MP4、清单及内容哈希按原字节保存；归一化缓存另存。作者工具只检查结构，Windows 导入器的解码验证是最终依据。
- 正常单屏编辑里原有“更换素材脱离包时间轴”的明确提示仍保留；需要与整机场景同步的新视频使用 v3 包绑定到共同时间轴。原生传输策略本身不解除 `TimelineId`。

## 设备指令与恢复

保持既有图片命令白名单。新建独立的类型化 TURZX 视频协议，只提供经过主源核对的流启动、数据、队列查询及停止；没有任意 opcode/RGB/固件/存储写入入口。初始化不改安装方向、背光或设备持久设置，不照搬参考脚本里的改亮度步骤。

每次只有一个工作线程和现有一个 WinUSB 连接拥有设备；每次最多一个访问单元在途。数据以不超过 202752 字节的块发送，逐笔匹配命令与请求时间戳。实际原厂 .NET 发送器的缓冲高/低水位为 `>3` 后等待到 `<=2`，其中单位尚不能当作呈现帧数；参考 Python 示例的比较方向相反，未直接照搬。等待和控制清理均有上限。

试验支持 1–60 秒和 1–60 目标 FPS，限定已在运行的 TURZX；可临时使用等循环时长的测试素材，但保留当前 `TimelineId`。不修改保存的场景/本机设置。场景切换、设置保存、停止、故障和到期都会结束临时覆盖；素材删除与试验入口共用生存期事务，活动试验素材受保护。统一时间轴阻塞时发明确黑帧，不继续播放缓存内容或偷换本地时钟。

所有停止路径均尝试退出原生流；普通图片路径重新发送**当时最新**内容，不恢复陈旧场景备份。现有五屏背光关闭和恢复门槛保持。原生预览会解码实际 H.264 访问单元，再合成实际 PNG 信息层；超预算或失败明确报告。

## 依赖及实现核验

采用 MIT 许可的 Vortice.MediaFoundation/DirectX 3.6.2、Vortice.Mathematics 1.9.2、SharpGen.Runtime/COM 2.2.0-beta。选择该版本是为了保留现有 .NET 8/System.Text.Json 基础栈；评估过的 3.8.x 会带入 JSON 9，因此未采用。SharpGen 的传递版本是 beta，完整记录并运行互操作回归，不称为微软认证组件。许可文本随程序输出。

编码/解码显式选择 Windows inbox H.264 MFT。离线原型已验证原生 480×1920、每帧 IDR、独立解码与 RGB 原色。绑定库输出结构会为调用者提供的同一个样本再创建包装对象；本实现直接使用固定 `IMFTransform::ProcessOutput` ABI 管理一份输出所有权，并补充循环编码与强制 GC 测试，避免输出资源所有权不明。

## 下午复测：黑位与颜色描述修正

用户确认正常播放/同步/叠加后再看一轮，发现仅长屏整体偏亮、黑色发白、对比度下降；测试结束恢复普通 PNG 后亮度恢复。两次均为 60 秒限时试验，原场景、屏幕场景和 23 个新鲜配置/保存记录文件保持不变。第二轮测试前一块 TL 屏已报 USB 写入超时 121，仍未把它算入健康跨屏对照。

排查没有发现背光/亮度设置写入：视频路径不发送背光命令14，源画面亮度均为1。实际四幅背景经旧 PNG 编码全部为全色、显示像素精确；H.264 在 Windows 正确解释电平时的平均亮度误差约 -0.13～-0.25 / 255，未发生主机侧整体增亮。因此不能把这次发白解释为降色减少或画质提高。

**明确发现的码流缺口：**Windows 编码器设置了 NV12 16～235 和颜色属性，但原 SPS 中没有写出范围、矩阵、原色和传递特性。独立 ffprobe 只能读到分辨率。灰阶输入的 Y 确为16～235；若设备按全范围解释，就会抬高黑位、压缩对比度。这个解释与用户现象一致，但固件的实际映射仍须通过修正后的硬件试验确认。

修正候选只补足本项目所产 Baseline SPS 的 Annex E 色彩描述：限范围、BT.709 原色/矩阵、对应合成画布的 sRGB 传递特性；不更改图片像素、亮度、PPS、压缩画面切片或现有时间/HRD字段。解析有大小、位数和语法边界，非受控 Baseline 明确拒绝。Windows 预览解码补上显式 SPS 触发的一次有界 NV12 输出协商。

独立工具已将候选识别为 `color_range=tv`、`color_space=bt709`、`color_transfer=iec61966-2-1`、`color_primaries=bt709`；四幅实际画面和灰阶的主机解码亮度与原结果一致。新增7项回归覆盖 SPS 幂等、其它 NAL 字节保留、畸形输入拒绝及真实黑/灰/白解码误差，连同已有原生视频测试共16项通过。初次分析器与预览格式变化失败保留。完整回归和候选部署/实机对比结果待下方收口，不把离线通过当作设备黑位已修复。

### 试验结果与最终全范围修正
