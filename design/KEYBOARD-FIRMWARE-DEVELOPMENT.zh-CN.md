# 键盘固件内容开发规范

本文件保留功能开发时的协议基线和历史验证入口。文中 `bringup/` 路径属于开发机私有证据，不随源码仓库或安装包分发，也不能作为部署环境的依赖。通用软件升级器位于 `src/UnifiedRgb.Firmware*`，默认禁止硬件执行；本仓库不包含定制固件镜像、设备绑定或安装授权。新的设备、传输路线和发行包均需独立验证。

本规范用于在现有 ROG 键盘中新增 OLED 页面、图案和受控输入动作，同时保留原厂功能与光域页面。每次内容扩展都应交付一套可复现的源码、固件、Host 契约、验证结果和可回退发行包；刷机界面只负责执行已经审核的发行包。

**固件发行审核和一次真实安装是两件事。** 发行包固定内容与执行器身份；安装时重新建立当前实物、USB 升级会话、备份、操作授权和事务日志。旧安装记录可以作历史证据，不能变成下一次安装的授权。

## 1 适用范围与当前基线

当前已观察的 APP 范围为半开区间 `0x1C000..0x53000`，大小 **225280 字节**，包含 **55 个 4096 字节页面**。最后四字节 `0x52FFC..0x53000` 为小端加和校验字：前 56319 个小端 `uint32` 的和按模 `2^32` 截断。更新流程只允许这个 APP 范围，不包含 Bootloader、用户配置、SoftDevice 或外部存储。

| 参考镜像 | 用途 | 不能据此假定的事 |
| --- | --- | --- |
| 原厂 `B521…98121` | 还原原厂指令、构造功能补丁的来源 | 不是当前键盘必然运行的镜像，也不是每次安装的默认回退目标 |
| 功能版 `0D7C…341958` | 已有光域 Mode9 的功能源码基线 | 不是装入新 Logo 后的完整当前镜像 |
| Logo 版 `2DCB…9239675` | 当前已安装记录所对应的 Mode9 与 Logo 基线 | 历史安装成功不能代替本次新鲜设备检查或本次固件验证 |

完整 SHA256 以发行清单和实际文件计算值为准。普通查询仍可能返回原厂版本 `0.25`；不能伪造版本字节，也不能靠“版本号相同”判断功能固件相同。

当前用户已确认继续使用我们的 `0.25` 开发固件，允许沿用既有基线经验与备份证据。本次准备不为重新证明这件事重复查询身份、版本或读取完整当前 APP。记录应写明“用户确认沿用”或指向已有安装记录，不得把保留镜像改名为新鲜读取；对新候选、源码、包和事务的审核仍单独进行。

当前参考源码在 `bringup/astra-logo-entry-fix-20261029/snapshot/firmware/native9`。它的功能代码与 `0D7` 一致，Logo 数组与当前 `2DCB` 相符。历史源码、输入镜像、安装授权和日志均保持不可变；新内容一律在新的隔离目录中开发。

## 2 页面登记与输入动作

新增页面先填写 `keyboard-page-change.template.md`，再改代码。每页应有稳定 ID、显示名称、所需能力位、入页图案、待机内容、离页行为和允许的输入意图。

页面信息集中登记，不在多个函数里各写一套“最大模式号”。`native-page-registry.template.json` 给出本次 `9/10` 的登记种子：明确的 ID 与能力要求、允许的输入和 typed intent、入页素材和保持、无 Host 回退、Host renderer、电源关系以及准入证明。固件选择器、Host 解析器和测试向量分别消费同一份已审核的页面定义，但反例与最终指令检查仍应独立。

| 页面 | 内容与动作 | 当前要求 |
| --- | --- | --- |
| 原厂 `0..8` | 保留原厂页面语义、映射和持久化行为 | 不把新增页 ID 写入原厂数组或持久化槽 |
| 光域 `9` | 原场景图案、动画、状态与临时场景提示；原有上下拨和按压功能 | 新页面不能覆盖它的图案、场景绑定、时钟与电源策略 |
| Codex `10` | 入页 Logo 和 `CODEX` 名字，随后显示进度条内百分比与重置时间；按压提交打开电脑 Codex 的专用意图 | 与机箱熄灯独立；不能触发光域的场景切换或机箱开关 |

物理页面循环的当前扩展目标为 `7 → 9 → 10 → 原有重置路径`。两个原厂循环分支必须同时修改并验证，不能只改一个计数上限。页面 `10` 的存在不代表 `11` 及以上也被允许。

下一页 `11` 及以后默认拒绝。只有登记、能力或版本契约、固件范围与持久化、Host renderer、输入意图和完整跨页反例全部扩展后才可启用。能力位用尽或固定报文的保留字段需要改变时，应设计明确的新契约；不能用一个诊断 build 号代替能力协商，也不能把 `mode <= max` 当作功能准入。

输入处理应分成“解析有效输入”和“派发页面意图”两层。底层继续验证 neutral、序列号、profile、epoch、cookie 和 transport；上层按当前页面把按压映射为明确的动作类型。不得把原始键值、页面名称、包内命令行或网络返回值拼成 shell 命令。打开 Codex 等电脑动作只能指向已安装、受信任的固定目标，并限制一次有效按压至多提交一次。

报文的 `reportSequence` 与 Host 已接受动作的 `acceptedIntentGeneration` 是不同概念。合法的抬起 neutral 或保持报文可以继续增加报文序列号，不应仅因此取消已经接受的按压。排队动作在启动前核对当前页面、上下文、消费者 revision、维护 gate、新鲜度和显式取消代次，而不是要求当前报文序列仍恰好等于按压报文序列。底层仍严格验证下一个报文序列，意图去重仍拒绝重放；此区分不需要伪造 neutral 或增加一个固件报文字段。

硬件 Host 可以因设备控制而以管理员权限运行，本项目规定普通电脑界面仍通过已核验的同用户、同交互会话、medium integrity 且未提升的桌面 broker 打开。Codex 的固定目标为已安装应用的 AUMID `OpenAI.Codex_2p2nqsd0c76g0!App`；页面内容与发行包不能覆盖它或注入参数。broker 身份、会话和权限验证失败时报告不可用，不能退回管理员界面、`runas`、UAC、其他用户身份或请求凭据的启动方式。Windows 的既有 Explorer 桌面启动方案见 [Microsoft 说明](https://devblogs.microsoft.com/oldnewthing/20131118-00/?p=2643/)。

## 3 兼容契约

当前 OLED 契约为 `GYM1`、协议 `2`、`208×64`、16 级灰度、每帧 **6656 字节**。每字节低四位对应偶数像素，高四位对应奇数像素。控制报告维持现有规范化 `65/RID0`；无线底层报告和输入集合继续遵守各自实际报告长度与 RID，不能把两种长度混用。

Codex 独立页使用能力位 `0x40`，已有同 epoch 画面能力位 `0x20` 保留。`0x25314D50` 是本次设计中的诊断 build 标记，不是 Host 准入凭据。兼容规则为：

- 旧固件没有 `0x40` 时，原 Mode9 按既有规则工作，不自动获得 Mode10。
- Mode10 同时满足明确的能力位、几何、协议、生命周期和实际页面检查后才可 ARM。
- ARM 请求中的预期页面必须等于新鲜 CAP 返回的实际页面，不能继续写死为 `9`，也不能仅把常量全局替换成 `10`。
- `9 ↔ 10` 切换必须使旧控制与上传上下文失效。旧 cookie、旧 epoch、旧按压、旧帧和半帧不能跨页复用。
- 未知页面、未知协议、无效几何、非预期 profile、畸形或负应答维持拒绝。不能为了新页面忽略异常报文。
- Host 应容忍未理解的可选诊断信息，但不能凭未识别能力位派发新动作。功能能力与诊断 build 的判断必须分开。

每个发行包附上与**最终镜像**同批的 wire contract 和真实编译 C 生产者向量。报告解析测试应使用这些向量和独立反例，不能只让 C 与 C# 共享同一段可能出错的编码实现。

## 4 图案与入页呈现

先明确图案是静态资源还是主机实时内容。像 Codex 额度这样的数据由 Host 后台采集并缓存；OLED actor 只读取已经准备好的像素。固件断开 Host 时可以显示名字、Logo 或“等待连接”，不能画出假额度或把未知值当作零。

入页 Logo 的来源和计时起点应只有一个。键盘已经绘制原生 Logo 时，Host 不应再次上传相同 Logo 并重新计时；如果 Logo 由 Host 上传，显示保持应从完成上传后的确认点计时。入页保持、当前数据切入和再次入页的行为都要测试，不能靠反复重传延长 Logo。

素材应优先复用受信任的矢量或紧凑遮罩。`48×48` 的单色遮罩只需 288 字节，可以在固件中展开到灰度画布；不应为了一个小 Logo 额外嵌入整帧 6656 字节。实际格式、遮罩尺寸、步幅、目的缓冲和展开边界随清单固定，必须验证全零、全满和边缘坐标。

本次 Codex Logo 来自协调者提供的官方已安装应用资源，准备为 `codex-logo-48x48-msb.bin` 的 48×48 高位优先单色遮罩。素材来源、编码、文件 hash 和最终固件中对应数组的 hash 应一起记录；不要由固件开发者重新描摹一个相似图标后当成同一素材。

光域原 Logo、原场景素材及其绑定保留为独立资源。Codex 页面不叠加光域场景名称、机箱状态或光域入页标志。页面临时退出后，场景动画回到当前共享相位，不能重新从第零帧播放。

额度页的正常画面只包含百分比进度条与绝对重置时间；采样时间可在内部用于判断新旧，但不显示“最近成功”。查询失败时旧数字必须明确标成旧数据；重置时间经过后旧窗口失效，不能当成新的额度。窗口名称和数量来自实际数据，不能假定 primary 永远是五小时，也不能把多个窗口百分比相加。

## 5 Host 与设备所有权

整个键盘仍只有一个 OLED 与 RGB 控制 actor。新增页面不得另开 HID writer、单独续租线程或并行数据上传器。CAP、ARM、上传、输入 reader、续租与恢复继续在既有事务边界上串行进行，前一个 reader 必须取消并 join 后才能进入下一个控制事务。

光域控制请求和 Codex 页面请求是独立消费者。关闭光域控制不应自动关闭已请求的 Codex 页面；只请求 Codex 也不能使 Mode9 获得控制权限。维护交接、会话恢复和 request revision 必须观察消费者变化；页面内动作还要再次校验当前页面，防止排队的光域动作在 Codex 页执行。

电脑程序里的 Codex 设置应放在独立标签页，邻接现有“显示与动画”；固件更新也有独立入口。Codex 页只设置自己的数据和打开应用行为，不改场景动画偏好；刷机页加载包时不进入设备或生成操作授权。开发规范应从固件更新页直接打开，且随程序安装，不依赖私人 `bringup` 路径。

数据查询、解码、缩放、文字绘制和文件读取均在 actor 外执行。actor 只接收不可变的、长度已检查的缓存帧；相同像素不重复上传。以 Codex 为例，后台成功查询间隔下限为 60 秒，失败退避至 60、120、240、300 秒，具体值由源码和发行记录固定。

桌面启动请求分为排队、提交启动和实际完成三个阶段。排队项在最终启动边界重新检查页面、消费者、维护交接、上下文和新鲜度；失效后可以取消且不能调用 broker。启动已经提交后，页面退出或取消无法可靠撤回系统调用，应保留 `Unknown` 或运行中状态，等待真实返回；不自动重试未知结果，不让同一槽位再启动第二个请求。调用 broker 时不得占用设备 actor 或协调者的锁。

每个实际启动任务都由协调者保存和观察。`Stop` 先停止接收并使排队项失效，再在锁外等待已经提交的调用结束；`Dispose`、GUI 断开和关闭窗口不能丢弃运行任务或提前声称空闲。若等待期限已到而调用尚未结束，仍保留 busy 与未知结果，不能将超时当作已 join。启动 API 返回成功仅表示请求已被接受，不表示窗口已出现或获得前台焦点。

现有 USB 与无线 OLED 整帧传输会占用共享通道并可能暂停 RGB。降低主机帧间隔、提高软件写入计数或获得协议 ACK，都不能证明更高可见帧率、无线稳定性或 OLED 与灯光光学同步。未建立新的协议与物理证据前，不增加图块交错、削短等待或绕过现有预算。

## 6 内存与链接边界

当前参考链接脚本固定以下边界；新发行必须重新验证最终 ELF，而不是抄写旧清单。

| 项目 | 参考约束 | 必须交付的证据 |
| --- | --- | --- |
| owned ROM | 起点 `0x4EA64`，末端不越过 `0x52FFC` | `.text` 与 `.rodata` 的地址、大小、结束地址和剩余空间 |
| 自定义状态 | `0x2003A780..0x2003A7A0`，32 字节，NOLOAD | `sizeof`、关键字段偏移、section 地址与类型 |
| 栈相关补丁 | `0x1C000`、`0x1C214` 等既有审核点 | 实际补丁字节、编译器 `.su`、veneer 和嵌套路径测量 |
| 跳转与续接 | 每个补丁点对应最终符号地址 | 反汇编后的跳转目标、Thumb 位、调用者 LR、保存与恢复寄存器和续接地址 |
| OLED 缓冲 | 6656 字节与既有规范化收发边界 | 首末字节、步幅、行数、片段长度、目的地址与别名检查 |

编译器单函数栈大小、受控片段的嵌套栈测量和完整固件 IRQ 高水位是不同证据。完整 IRQ 高水位未闭合时应明确记录该限制，不能由局部 ABI 测试推导为整机栈已验证。

## 7 功能补丁与素材补丁

纯素材补丁可以沿用已有代码与符号地址，但必须证明所有变化只在被审核的素材区间和校验字内，且代码段、全局符号和普通功能完全不变。

新增页面属于功能补丁。必须重新链接 owned 代码，重算每个补丁点的分支目标，并将最终镜像与实际回退基线逐字节比较。允许变化的范围应明确列出，范围外出现任何差异都阻止发行。

当前参考的完整功能生成器为 `bringup/kimi-native-entry-logo-20261029/snapshot/baseline/firmware/native9/assemble25.py`。它构造 30 个补丁点，检查 APP 长度、原始字节、链接符号、变更范围和校验字。后续 `build_asset_candidate.py` 是仅修改 Logo 的构建器，并且断言代码不变；不能用它产生新增 Mode10 的功能镜像。

历史 `NATIVE9-FINAL-PROOF.json` 等文件可能绑定不同 build 或不同候选 SHA。即使文件名相同、测试数量很大，也只有镜像 SHA、ELF、源码、契约和工具版本全部对应本次发行时才算本次证据。修改 Logo、字体或一个分支后，受镜像 hash 约束的报告都要重新生成。

## 8 验证矩阵

| 层级 | 应覆盖的内容 | 结论边界 |
| --- | --- | --- |
| Host 原生 C 测试 | 状态机、ARM、neutral、序列、跨页失效、持久化、片段与边界反例 | 证明被测 C 逻辑，不等于执行最终 Thumb 镜像 |
| 最终 ELF 静态检查 | section、符号、30 个实际补丁点、stock 字节、允许差异、校验字 | 证明本次镜像结构，不等于设备运行 |
| veneer 与 C wrapper 执行 | 最终 Thumb 指令、敌对桩、寄存器恢复、LR、续接和局部栈 | 桩替代的部分必须列明，不能称作完整原厂代码执行 |
| 实际 stock 片段重放 | 已固定原厂指令与自定义 CAP、ARM、RF 分发、复制、渲染的组合 | 只对重放覆盖的路径负责，不代表完整 IRQ 调度 |
| Host fake 与 IPC 测试 | 单 owner、页级准入、旧固件、跨页重放、动作隔离、消费者、维护和恢复、UI 不自动写入 | 不等于 USB 或 RF 物理行为 |
| 安装器 fake 与拒绝测试 | 错包、错设备、过期 pin、错 hash、备份失败、磁盘耗尽、取消、未知结果、父事务回退 | 不等于真实刷写与物理回退已完成 |
| 真实安装与回读 | 当前同一设备、全部页面、完整目标与校验字 | 是传输与内容验证，不等于每个视觉或按键功能都验收 |
| 用户物理验收 | 两种连接、原厂页面、光域图案和拨杆、Codex 入页与额度、跨页按压、睡醒和回退 | 按实际观察记录范围与时长，不扩大为永久稳定性 |

最小负例应包括未声明 Mode10 能力、未知页面、错误 profile、旧 epoch/cookie、重复或跳号输入、半帧切页、旧帧复用、错误片段长度、无效目的地址、畸形/负应答、超时、reader 未 join、恢复目标变化和事务日志未决。失败日志及第一次失败的 TRX 保留，后续通过不能把最初的失败改写成一次全绿运行。

## 9 可复现工作顺序

1. 从当前实际基线创建隔离源码目录，固定原厂来源、当前回退镜像、Logo、契约、工具链与源码 hash；保留主仓库已有的未提交修改。
2. 先填写页面登记和 Host 意图边界，再修改固件与 Host。协议变更同时更新 C 生产者向量、C# 解析器、兼容规则和反例。
3. 在新目录执行发行提供的构建及 proof 入口，所有缓存和输出留在该目录；禁止在历史快照原地重跑并覆盖证据。
4. 严格构建固件及相关 .NET 项目，保留 warnings as errors；按变更运行相关测试，不通过修改无关测试、放宽范围或忽略缺失输入取得“通过”。
5. 独立检查最终 ELF、镜像差异、内存与栈报告、wire contract 和安装器准入，得到精确镜像绑定的软件审核记录。
6. 生成自包含的准备包；刷机页离线加载它，只进行包格式、hash、信任目录和兼容性检查。
7. 只有用户明确开始本次安装或恢复时，才进入维护交接与当前 USB 升级会话，建立新鲜物理绑定与操作记录。
8. 写入前读取并固定当前完整镜像，执行事务、整页回读、完整目标回读与校验字验证；完成后才报告安装成功。
9. 记录实际运行与物理验收。恢复原程序连接或重新打开 GUI 时保留用户当前场景、本机设置与草稿。

历史构建路径可用于寻找入口，不能直接作为新包运行时依赖。当前功能源码目录中的 `build.py`、`assemble25.py`、`verify_native9_sites.py`、`verify_local_abi25.py`、`verify_wrappers25.py` 和相关渲染、RF、producer 脚本提供了已有验证思路；新发行应提供适配本次页面与 hash 的统一入口。

普通软件验证使用项目实际 .NET SDK，并把输出放到隔离 artifacts 目录，例如：

```powershell
dotnet build '<隔离源码>\src\UnifiedRgb.Host\UnifiedRgb.Host.csproj' `
  -c Release -warnaserror --artifacts-path '<隔离目录>\artifacts'
```

固件构建的 Zig 版本与二进制 SHA 也应由构建入口固定；不可因本机 PATH 改变而静默换编译器。不得把这些构建命令、历史审核脚本或带过期 pin 的 CLI 参数接到用户刷机按钮上。

## 10 准备包与信任

准备包采用刷机模块实际支持的 `Schema: 1`、分类 `UNIFIEDRGB_KEYBOARD_APP_RELEASE_V1`。所有路径相对于包根，所有文件都绑定 SHA256。当前安装容器只允许 `release.json` 及它引用的五份数据：候选 APP、允许的回退 APP、功能镜像清单、刷写 wire contract 和软件审核记录。不得在 ZIP 中塞入可执行文件、信任目录、授权、设备 pin 或未引用的附件。

开发交付目录另外保留源码与构建说明、完整 GYM1 页面契约、全部验证结果及证据索引。容器里的 `ReleaseWireContract` 描述 R6 刷写协议，不等于 OLED 的 GYM1 页面契约；两者必须分别审查。软件审核与独立本地信任目录绑定最终安装容器、相关数据、worker core manifest 与安装 worker 的精确身份。安装容器不执行开发目录中的脚本。

目标信息固定正常型号 `1C24`、升级型号 `1C26`、升级原始版本 `02000200`、APP 范围和 `OFFICIAL_4K_ALL55_V1` 页面策略。它们只是包的兼容条件，不能代替当前实物身份。新增不同型号、Boot 协议或区域必须作为新的审核工作，不能扩大现有允许列表后自动继承旧结论。

软件应从**独立安装的本地审核目录或受信任发布者**选择 worker 身份。包里携带一个“信任目录”或声称自己审核通过，不会获得执行权限。未知包默认拒绝；导入 ZIP 不能扩展信任根、生成新授权或启动包内任意程序。未来采用发布签名时，公钥必须从包外安装，私钥保存在原生凭据或受保护的签名系统中。

本地目录的 `CatalogEntry` 可以附带可选 `RetainedBaseline`，实际字段为 `Label`、`Image { Path, Sha256 }` 和 `Receipt { Path, Sha256 }`。它的 receipt 使用 `UNIFIEDRGB_OWNER_CONFIRMED_RETAINED_BASELINE_V1`，记录镜像 hash、正常型号和 header、正常设备的 ContainerId 与物理端口、用户确认时间和证据说明。此来源叫 `OwnerConfirmedExistingReceipt`，与真正双遍读取的 `ActualTwoPassRead` 分开。保存正常身份是为了后续正确目标绑定，不代表升级时 ContainerId 必须相同；这些实物值留在本机记录，不写入通用模板。

沿用记录不能被导入包自带的声明替代，也不能由一个勾选框伪造为新鲜读回。它允许跳过重复的基线发现或额外单独 M 备份，实际安装事务仍在写入前执行自己的内容一致性和不可变 before image 阶段。

加载器应限制文件数量和总展开大小，并拒绝绝对路径、`..`、路径别名、重复文件、大小写碰撞及跳出包根的重解析路径。先在私有暂存目录完成校验，再提交不可变安装计划；真正写入前再次核对用于执行的文件，避免检查后换包。

准备包不得包含旧 `INSTALL-APPROVAL.json`、设备 pin、HID 路径、ContainerId、旧 run ID、用户凭据或“已物理验收”的模板值。模板与说明只能是明确不可安装的草稿；实际发布清单必须由构建与审核结果产生。

## 11 刷机和回退事务

### 自动进入升级模式

本机 AZOTH X 正常 USB 路径的官方来源已确认：VID0B05、PID1C24、UsagePageFF00、Usage1，普通 64 字节 HID payload 无报告 ID。Windows 一次性 OUT 缓冲为 `00 7B AA 41 53 55 53 AA` 后补 57 个零，总长 65 字节；它触发正常固件的原有进入升级路径，而不是在 APP 模式直接擦写。

这条路径没有普通 HID ACK 预期，不能通过 OLED `ExchangeAsync` 发送。只有用户明确开始自动准备、当前目标元数据匹配且本次维护已释放旧会话后，才可发送编译固定的一次性命令；包、RPC 和用户可编辑文本不能提供命令字节。发送前持久化转换意图，写操作无论完成还是未知都要 join 并关闭旧正常句柄，然后只观察匹配升级目标。未知完成不能成为再次发送的理由。

后续以连续、排他的正常目标消失与同一完整 USB 物理端口上唯一升级目标出现为见证，再建立新的 PID1C26 升级身份。正常和升级 ContainerId、HID 路径或 USB ancestor 可以不同，必须保留真实值，不能伪造相等或把任何同 PID 设备当作当前目标。官方名义等待为 30 次、每次 1 秒；本程序应有实际总期限，不把名义时间当作硬保证。手动入口保留为显式恢复选择，不是未知结果后的自动重试。

官方的相同版本跳过策略不适用于继续保持 OEM0.25 的自定义内容更新。应按已审核的发行与镜像身份判断，不能因为 header 相同跳过新候选，也不能伪造版本字节来绕过旧判断。官方 DLL 的 pending write、取消和错误处理较弱，不应照搬；本程序保留原有精确 I/O、join、事务和日志约束。此证据只覆盖进入升级，不能顺便加入未单独审核的退出、复位或其他型号命令。

进入命令和原厂处理的静态证据见 `bringup/official-normal-to-boot-20261102/HANDOFF.json`。当前已确认基线和准备候选的相关源代码区间均保留此路径，但尚未在本次工作中进行物理自动进入测试；设备内部 stock quiesce 的全部 NVM 副作用也未闭合，不能宣称零内部持久化影响。

### 擦写与完成

当前已审核路径为 USB APP 全 55 页，不支持“只改了几个页面所以只刷几个页面”的隐含优化，也不通过无线或蓝牙升级。页面编程可用 4096 字节暂存，但回读仍是经过验证的 32 字节路径；不能把写入 4 KiB 推断为读取也能 4 KiB。

界面按阶段报告“校验包、等待设备、交接、读取备份、擦写页面、完整验证、等待正常重连”。百分比应来自真实阶段或已验证页数。进度条到末端、OUT 完成、进程退出码为零或文件存在，都不足以单独宣布成功；最终状态应绑定完整目标回读与校验字结果。

真实操作前必须满足：

- Host 已完成当前请求的交接，接口释放得到明确确认；不能在交接未完成时强杀 Host 或另开设备句柄。
- 当前正常设备与升级设备的物理绑定符合审核策略，型号、集合、报告能力、同一实物和当前会话均匹配。
- 当前物理操作 pin 的年龄按实际捕获时间计算。历史已有 15 分钟当前会话准入与单独的保留镜像证据策略；这些是不同规则，不能刷新时间戳把旧证据变新。沿用已确认的固件基线不等于冒用另一台设备或旧升级会话。
- 候选、回退、manifest、contract、review、runner 和 core manifest 全部重新核对；新的 run ID 和空日志不能与旧事务混用。
- 真实安装事务继续执行其已审核的当前内容检查、不可变 before image 和 lineage 持久化。参考 R6 核心在擦写前做两次完整读取；这是实际破坏事务的一致性阶段，与本次已免除的额外基线重审或单独 M 备份不是一回事。不能在“准备固件”阶段偷偷启动这些真实设备操作。

事务应先持久化 `EraseIntent` 或 `ProgramIntent`，再发送恰好一次破坏命令，完成限定的状态与内容验证后才写入对应的已确定记录。日志、trace 和命令预算应在发意图前预留；不能写到一半才发现记录空间不足。

**未知破坏结果必须冻结后续 I/O。** 取消、超时、断电、读回不一致或日志写入失败若发生在破坏意图之后，不能自动重发、重置设备、改变参数、切页面、继续探测或“失败就自动回退”。UI 应显示需保留现场与日志，禁用普通重试，交由有证据的恢复路径处理。

普通回退也要核对同一物理设备、父安装 ledger、run、lineage 和原始 before image。不能从任意旧备份开始写回；新装候选的回退对象是本次确切 before image，而不是固定选择原厂镜像。恢复了 APP 不等于可以删除用户配置、场景、映射或校准文件。

## 12 发行完成条件

软件准备完成应同时具有：可复现源码与工具链、精确候选及回退文件、已核对的契约、全部相关验证结果、独立审核记录、自包含准备包、可用的包加载与拒绝 UI、明确的恢复路径和剩余物理验收项。

“准备完成”“可开始一次受限安装”“安装回读成功”“用户接受当前功能”和“长期稳定”应使用不同字段与文案。不能把前一阶段的通过自动提升为后一阶段。

每次内容扩展最后更新项目交接文档和当前指针，记录实际部署的二进制与设置 hash、保留的失败、用户实际观察和正在运行的工作。关机属于用户运行安排，不属于固件流程；只有用户已授权且所有相关工作、外部模型任务、观察任务及其他需要该电脑的聊天均结束时，协调者才能执行。
