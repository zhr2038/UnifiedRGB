# Wireless TL：原生协议核实、60fps实测与JPEG画质策略

日期：2026-10-21。目标是提升三块风扇屏的实际播放能力，不依赖厂商程序，保留现场场景、本机配置和熄灯状态。

## 结果

- 通过同系列固件分析和本机只读查询，三屏均回报 `tlv2_2024091005_01`。没有发现有效原生H.264流能力；未把通用应答当支持，也未刷固件。
- 现有MP4解码/JPEG通道能够运行真正60fps素材：960幅不同画面、精确16000ms，三屏均约59.56次主机事务/秒。用户确认“三块都流畅，画面正常”。不是把30fps重复发送当60fps，也没有宣称相机实测每秒呈现60幅。
- 增加独立可选 `jpeg-detail-v1`：现有JPEG容量内从Q100起步，超预算有界回退；旧默认字节和场景不变。原素材实机A/B后，用户确认“能看出细节改善”。
- 本机完整回归2448项通过，后台与界面磁盘文件已更新；当前界面没有重开，草稿保留，新选项在下次启动出现。结束后重新熄灯，原常用策略恢复。

## 为什么不直接套用冷头/FLEX视频协议

Wireless TL是VID1CBE/PID0006，实际固件版本见上，不是FLEX A018/A019。保留的官方 `tlv2_2024091005` 更新样本是MIPS/Linux用户态程序；它不是本机完整闪存转储，版本字符串吻合也不等于本机字节哈希已经读回。

样本的命令分派包含JPEG101、文件写入40和工厂测试253，没有121/122/123视频流接收/查询/停止处理；`handle_data_thread`直接返回。253会启动外部程序读取 `/media/out.h264`，并设置影响USB连接变化时背光联动的测试标志。文件上传会 `fwrite`、`sync`、关闭文件，不能当成没有设备存储影响的流发送。

实际只读探针只允许版本10、视频块查询17及版本分支128。三屏都返回旧版本，17的有效返回容量为0；500字节加尾标的新式视频块/版本查询没有有效回应。某个分支的普通C8应答没有有效能力数据，未据此开放视频。最后再次读取旧版版本，确认通信仍可用。没有发送121视频、253工厂测试、文件上传、存储、固件或重启命令。

查询期间短暂停止唯一的真实Host，诊断工具退出后立即重开；没有第二个硬件Host，也没有新UAC。正常查询和恢复共约10.6秒，11747个保护文件不变，五屏保持休眠。初版探针被生产图片接口白名单拒绝，没有发出查询；未放宽该白名单，另用固定只读查询封装，并先做六组帧头离线检查。此前脚本预检失败和被拒记录保留。

因此，H.264解码工具的存在是继续研究固件的线索，尚不是可安全上传、停止和恢复的USB流接口。若继续做设备原生H.264，需要扩展同系列设备端程序并先解决完整恢复办法；本轮没有在日用设备上安装自制固件。

## 真正60fps素材与实机数据

先用现有30fps R23做5秒60Hz发送试验，只用于测吞吐，明确不作为独立60fps画面证明。随后离线制作通用深色运动测试图：青色移动条、黄色圆点和逐帧编号。MP4为400×400、960帧、16秒、667286字节，源SHA256 `472cc53549d22470eb6f27ed04f9b60a64b889670aa213088876a141d7472b47`。

通过产品Windows Media Foundation导入后，仍是960帧、960个不同规范化PNG、16000ms，驻留值16/17ms，规范化数据35403777字节。不是重复30fps、GIF升采样或只改帧率标签。素材制作工具仅用于离线验证，没有成为产品运行依赖。

60秒试验三屏临时使用这一素材并保留原共同TimelineId，其它屏幕与灯光继续原场景。119次采样无屏幕错误。只取目标60且试验ID匹配的活跃窗口：

| 指标（每块） | 结果 |
| --- | ---: |
| 活跃窗口跨度 | 59.331秒 |
| 完成事务增量 | 3534 |
| 主机事务速率 | 59.564次/秒 |
| 传输丢帧计数增量 | 0 |
| 调度跳过计数增量 | 25 |

调度跳过仍如实保留；“无传输错误”不代表每个源画面都被呈现。试验结束/恢复30目标后的滚动FPS会混入新节奏，不能取那个快照作60fps稳态统计。用户的流畅度确认是实际观察，不是光学呈现帧号或高速相机证明。

试验后恢复原屏幕内容，删除临时资产，重新全机熄灯。当前R23仍为原30fps素材、原发送配置，没有自动插帧、改写包或假装变成60fps。后续主题可用v3 MP4轨道已有 `fps: 60` 和真正60fps动作源；它不要求新的场景契约或设备固件。

## JPEG细节优先：保持协议和默认

三份当前素材共1440帧逐幅检查，明确解码实际JPEG字节后比较：

| 项目 | Q90旧策略 | Q100候选 |
| --- | ---: | ---: |
| 三份素材总JPEG数据 | 8899436字节 | 17943260字节 |
| 最大单幅 | 29455字节 | 78671字节 |
| 各屏平均RGB绝对误差范围（0..255） | 0.2144～0.2297 | 0.1296～0.1354 |
| 各屏PSNR | 48.10～48.50dB | 52.01～52.26dB |
| 超过101888字节上限的帧 | 0 | 0 |

平均像素误差约降低40%，不能写成观感提升40%。编码平均约0.32～0.40ms/帧，两档接近。离线对照总13.73秒，进程峰值常驻约80.56MiB，不是Host内存增量。两档均为原有Baseline JPEG、4:2:0采样，没有未经验证的新色型。

JPEG数据本身增大，但TL协议原本就是固定102400字节一包，仍只发送同样大小的一包，不增加USB包字节数。较大JPEG仍增加缓存占用或解码工作，不能泛称完全零成本；沿用原有有界缓存，新增策略不在共享时钟线程训练或读盘。

`jpeg-detail-v1`按100/95/90/80/70/60/50/40尝试，至多八次，只有容量内的完整JPEG可发送。适用于TL/H2，TURZX明确拒绝，不修改PNG阶梯或524288限制。新屏幕默认仍是legacy，旧默认和PNG保色策略下的JPEG输出逐字节保持。新策略只由显式保存本机设置启用，不进入包、原素材或内容哈希。

后台通过可省略的 `JpegDetailSupported` 字段通知界面。旧后台不提供该能力时，新界面不显示新选项；保存质量与应用内容保持独立。预览解码实际JPEG，不能显示未编码原图冒充。

实机先做5秒检查，再用原R23、原亮度/方向/30fps播放60秒。用户先确认画面正常并要求重播；随后在同一持续时间轴上用旧Q90约16秒，再切Q100约60秒，用户明确回复“能看出细节改善”。三屏活跃窗口约30次/秒，无屏幕错误、传输丢帧和调度跳过增量；原选择在熄灯后恢复，未自动永久切换。本轮实机质量验收针对三块TL，H2此策略只有软件回归。
